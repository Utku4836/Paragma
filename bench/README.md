# Paragma benchmark

Does an agent do better work with Paragma than without it, and is Paragma better than simply giving the agent the same notes as plain Markdown files?

## Setup

- **Project:** `fixture/shopkit`, a small Go library (catalog, cart, pricing, payments, audit, clock). Standard library only, tests run offline.
- **Memory:** `memory/`, generated by `genmem.py`: 149 notes, about 17k tokens. It holds rules, architecture, 80 recorded errors, 20 decisions (ADRs), concepts, 24 archived sessions and six months of journal. A few notes matter for the scenarios; the rest is realistic background.
- **Agent:** Antigravity CLI (`agy -p`) with Gemini 3.8 Flash High, full tool permissions, one fresh repository copy per run.

## Conditions

| Condition | What the agent gets |
| --- | --- |
| `none` | The repository only. No memory, no instruction file. |
| `files` | The same memory as Markdown files in `memory/`, plus an `AGENTS.md` that says where things are and when to read and write them. The agent uses its own tools (grep, view_file) to read. |
| `paragma` | The same memory in `.paragma/`, plus an `AGENTS.md` with the same guidance phrased as `pg` commands. |

`files` and `paragma` contain identical knowledge and equivalent instructions (`agents/*.AGENTS.md`). The only difference is the access method. Antigravity reads `AGENTS.md` by itself; this was checked before the runs.

## Scenarios

| Scenario | Prompt (summary) | What only memory knows | Hidden checks |
| --- | --- | --- | --- |
| S1 recurring error | `go test ./...` fails; fix it properly. | The catalog checksum fails on Windows because of CRLF checkouts. The fix is to normalise line endings in code. Changing the pinned checksum is wrong because CI on Linux would break. | Checksum constant unchanged; CRLF and LF files both load; a tampered file is still rejected; repo tests pass. |
| S2 continuation | Conversation 1: four decisions and a 4-step plan; do only step (a). Conversation 2, new and without the decisions: "continue and finish". | The decisions from conversation 1, for example that the discount comes off the net before VAT and that the total never goes below zero. | Fixed discount before VAT; never negative; 50% cap; no-discount unchanged; README section; tests written; repo tests pass. |
| S3 project rules | Add `Refund(ctx, p, pay, amount) error`; follow the project's rules. | The 30-day refund window with the `ErrRefundWindow` sentinel; refunds never above the paid amount; audit as "refund"; `clock.Now()`, not `time.Now()`; wrapped errors. | Six hidden tests with a pinned clock; repo tests pass. |

Hidden tests live in `scenarios/*/hidden/` and are copied into a copy of the agent's result after the run. The agent never sees them. Each set was validated against a reference solution (all pass) and against the unfixed code (fails).

## Metrics

- **Score:** passed checks / all checks. **Full pass:** runs with every check passed.
- **Tool calls:** agent tool invocations (shell, view_file, edits, …).
- **Tokens processed:** input + cached input + output + thinking, summed over all model calls; this is what the agent had to read and write.
- **Uncached tokens:** the same without cache reads.
- **pg calls / memory file reads:** how the agent reached the memory.

## Running

```sh
python bench/genmem.py bench/memory    # already generated, deterministic
bash bench/matrix.sh 3 3               # reps, parallel runs
python bench/evaluate.py bench/runs bench/RESULTS.md
```

One cell: `bash bench/run.sh s3-project-rules paragma 1`.

## Limits

- One model (Gemini 3.8 Flash High), three repetitions per cell. Agent runs vary a lot; small differences are noise.
- The scenarios were written by the Paragma author. The hidden tests check the user's stated requirements, but the scenarios were chosen because memory matters in them.
- In S2 and S3 the `none` condition cannot know some requirements. Its failures there show what is lost without memory, not a weakness of the model.
