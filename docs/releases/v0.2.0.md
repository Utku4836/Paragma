Paragma 0.2.0 is a new Paragma. It was rewritten from the ground up in Rust, around one question: what does a coding agent need at the start of a conversation, and how can it get that in a single call? The answer shaped every part of this release. Projects now carry their goal, steps and handoffs from one conversation to the next. Search understands meaning and other languages. Memory knows the code it talks about. Test runs come back with the fixes found before.

This note describes what changed, how it was measured, and what to expect when you install it.

## Install

```bash
npm install -g paragma
pg setup
```

npm downloads the build of `pg` for your computer from this release and checks it against `SHA256SUMS`. Builds are provided for Windows, macOS and Linux, each on x64 and arm64; the Linux builds are static and run on any distribution. You can also download a file below, put it on your `PATH`, and run `pg setup`.

### If you used Paragma 0.1

Paragma 0.2 keeps its notes in a new layout and does not read the notes of 0.1. If you installed 0.1, move or delete `~/.paragma` before the first run, then run `pg setup` again; it replaces the instructions 0.1 wrote into your agents' files. The commands have changed as well; the table at the end of this note lists the new ones.

## Work that continues across conversations

Most work takes more than one conversation, and the second one used to start without the first one's plan. In 0.2 a piece of work is a project with a goal, numbered steps and handoffs.

- `pg open <project> --goal "..." --step "..." --decision "..."` starts the work, or continues it when the project exists. Names written differently, with a typo or in another order still find the right project. The folder you work in is linked to it, so later commands there need no project name.
- The brief `pg open` prints is what a new conversation needs: the goal, the open steps with their numbers, the last handoff in full, what changed in the code since then, other conversations still working on the project, and the rules, decisions and past errors that match the goal and steps. It also names the project's stack, the test command, the code that likely matters and the narrowest tests to run first.
- `pg finish --done 1,3 "what changed, what is next"` closes the steps this conversation finished and leaves the handoff. Steps meant for later conversations stay open. Finishing again replaces the conversation's own handoff instead of adding a second one.
- Decisions given with `--decision` are kept as decision records, so a second conversation knows them even when the first one only did step one.

## Search

`pg find` takes a topic, a question, an error line, a file or a function name.

- Results come from full-text search and from meaning search, merged by rank. The embedding model, [potion-multilingual-128M](https://huggingface.co/minishlab/potion-multilingual-128M) by Minish Lab, is built into `pg`, reduced to Latin scripts and stored in 4 bits (39 MB). Nothing is downloaded at run time and no network is used.
- A question in Turkish, Spanish, German, French or Portuguese finds a note written in English. A small built-in glossary covers terms that models translate poorly.
- On our set of 70 questions in six languages against a memory of 1,335 notes, Paragma 0.1 found 77 of the 168 expected facts. Paragma 0.2 finds 153, uses fewer tokens per answer, and answers in about 95 milliseconds. Questions memory cannot answer return nothing instead of the nearest guess.
- A note shown in full to the same conversation in the last 90 minutes comes back as one line, so a conversation does not pay for the same note twice.

## Memory that knows the code

- tree-sitter reads 19 languages: Bash, C, C#, C++, Dart, GDScript, Go, Java, JavaScript, Kotlin, Lua, Luau, PHP, Python, Ruby, Rust, Swift, TypeScript and Zig. The first index of a large repository takes a few seconds; after that only changed files are read.
- `pg tree` maps the code: files, their functions and types, and the rules and errors about each.
- `pg read payments/refund.go#Refund` prints one function with the notes about it; `file:10-20` prints lines.
- Notes link to files and functions, and follow a function when it is renamed or moved.
- An error record remembers the state of the code it describes. When that code changes later, `find`, `read` and the brief say the note may be out of date.
- Decision and error records keep the commit they were written at.

## Test runs that remember

`pg run -- <command>` runs your tests or build and reads the output of go test, cargo, pytest, jest, vitest and dotnet.

- Each failing test is marked as new, still failing, flaky or fixed, with the function its error line points at.
- When memory has seen the error before, its cause and fix are printed next to it. Errors are matched by their message with numbers, paths and ids taken out, so the same error in another file or with other values is still recognised. When this project has no fix, other projects are searched.
- When no fix is known, `pg run` prints the `pg write --error` command to record one.
- Commands run with no input, stop after a time limit together with everything they started (`--timeout`, 600 seconds by default), and keep at most the first 2,000 and last 20,000 lines of output.

## Records

`pg write --rule`, `--decision` and `--error` keep what a project has learned.

- Writing a record that already exists in other words updates it instead of adding a copy. A record that negates or changes the numbers of an earlier one is never merged into it; Paragma points out the possible contradiction instead.
- An error seen often, in several files, is suggested as a rule.
- Notes of any length can be written from a file (`--file`) or standard input (`-`).
- Errors and notes not seen for three months are archived during `pg finish`, at most once a day. Rules and decisions are never archived on their own.

## Secrets

Each project has its own `<project>.env`. `pg write --secret "Npm publish token" -` keeps a key under a title; the agent finds it by that title and uses it as `$NPM_PUBLISH_TOKEN` in `pg run`, which puts the value in place on every platform and prints the name again wherever the value would appear. Keys pasted into notes are masked and not kept. In a test with 50 keys and ten requests in plain words, the right key came first every time and no value appeared in any output.

## Setup

`pg setup` opens a screen with the agents found on your computer: Claude Code, Codex, Antigravity and OpenCode, including their desktop apps. Choose an agent, then where Paragma should be read: in every conversation, in the folder of one conversation picked from the agent's own history (searchable by typing), or in the current folder. Arrow keys move, Enter goes on, Esc goes back.

The section Paragma writes is short and says when to call `pg`. Three skills hold the details and are read when needed: `pg skill coding`, `pg skill projects` and `pg skill knowledge`. When a later version of Paragma changes these instructions, `pg` updates the sections it wrote by itself, once, and leaves the rest of each file untouched.

For scripts: `pg setup <agent> --global`, `pg setup <agent> --dir <folder>`, `pg setup all --global`, `pg setup --list`.

## Measured with agents

We gave agents the same knowledge in two ways: as plain Markdown files read with their own tools, and through Paragma. Each run started from a fresh copy of a small Go project and a memory of 1,539 notes. Hidden tests the agents never saw checked the results.

| Agent and model | Tasks | Score, files → Paragma | Tokens processed | Tool calls | Time |
| --- | --- | --- | --- | --- | --- |
| Antigravity, Gemini 3.8 Flash | 5 questions | 5/5 → 5/5 | 1.95M → 0.32M | 76 → 22 | 8.6 → 3.2 min |
| Antigravity, Gemini 3.8 Flash | 3 coding tasks | 3/3 → 3/3 | 6.92M → 3.60M | 173 → 129 | 46 → 18 min |
| OpenCode, GLM-5.3 Flash | 2 coding tasks | 2/2 → 2/2 | 1.12M → 0.54M | 87 → 58 | 15 → 7 min |
| OpenCode, DeepSeek V4.1 Flash | 2 coding tasks | 2/2 → 1.88/2 | 1.35M → 0.73M | 83 → 79 | 4.4 → 5.0 min |

Paired by task and model, Paragma used fewer tokens in all 12 pairs; plain files needed 2.2 times the tokens, 1.5 times the tool calls and 2.2 times the time. In one run the result was not complete: DeepSeek, continuing work in a second conversation, chose a different type for one field because the first conversation had recorded only the step it was asked to do first. Every hidden test passed, but the check for the specified API did not. The instructions now ask for the whole plan and every decision to be recorded, and `pg open --decision` records them in one call. This change has not yet been measured with agents, and each cell ran once, so small differences should be read with care. The full setup is in [bench/RESULTS.md](https://github.com/Utku4836/Paragma/blob/main/bench/RESULTS.md).

## Reliability

- Many `pg` calls can run at the same time, from several conversations; writes wait for each other and reads never see a half-written note.
- Every command was run from three conversations at once, against notes in CRLF, BOM, UTF-16 and Latin-1, empty and very large files, binary files and symlink loops, and with twelve processes building the first code index together.
- `pg rm` moves notes to `.archive/` instead of deleting them. Indexes can be deleted at any time and are rebuilt.
- Tests run on Windows, macOS and Linux for every change. Before a release is published, each build writes and searches a note on a machine of its own platform; the Intel macOS build, made on Apple silicon, is the one exception.

## Known limits

- Meaning search covers Latin scripts. Notes in Chinese, Japanese, Russian or Arabic are found by their words only.
- `pg` is about 75 MB, most of it the search model and the language grammars. npm downloads only the build for your computer, compressed to about half that size.
- The first `pg` after `npm install` needs to reach github.com once if the install could not.
